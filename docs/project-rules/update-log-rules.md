# updateLog.md 更新规范

> 适用范围：`app/src/main/assets/web/help/md/updateLog.md`，App 内帮助文档与 CI 发布流程（`test.yml`）都以此为对外更新日志。
> 本文件是固定约定，不是状态记录；维护日志与发版前按它执行。

## 一、什么时候更新

- 完成一批 app 用户可见改动（bug 修复 / 界面修改 / 功能增加）后，随该批改动一起提交，不要求每个 commit 都产生一条。
- **发版前必须更新到最新**：`test.yml` 发布时会用 `updateLog.md` 生成 changelog，日志落后于实际功能会让发布页缺条目。

## 二、收录范围（用户可见判据）

核心判据一句话：**这次改动之后，用户打开 App 能不能看到任何不同？** 能 → 收；不能 → 不收。

| 收（写进日志）                                   | 不收（跳过）                                                                |
| ------------------------------------------------ | --------------------------------------------------------------------------- |
| bug 修复（崩溃、界面异常、行为错误）             | 纯 CI / 构建 / 依赖改动（spotless 门禁、commitlint、lint-staged、workflow） |
| 界面改造与 UI 重构（如顶栏统一接入新组件）       | 纯 docs / 规范 / 流程类提交（CLAUDE.md、docs/ 自身、提交规范、hooks）       |
| 功能新增与用户可见增强（新页面、新设置项、弹窗） | 内部实现细节（补 @OptIn / import、格式化、变量重命名、无行为变化的重构）    |
| 性能优化（用户体感改善）                         | 工程基建（.zcode、技能镜像、git 钩子脚本）                                  |
| 多语言补全（影响用户看到的文案）                 | 纯文档可读性修饰                                                            |

## 三、格式

- 按日期分组，最新在上：`**2026/9/11**`（日期格式与文件内既有写法保持一致）。
- 一天的多条改动聚合为一个条目，`- ` 开头、一行一条；前缀用 Conventional Commits 类型（`fix` / `feat` / `refactor` / `style` / `perf`），中文描述。
- 面向用户措辞：写"应用主题后页面卡死修复"，不写"消除重建风暴与竞态双重建（第 N 轮）"。
- 不写 commit hash、不写内部类名/变量、不堆无关感慨。没有可写的这一天就不新建空分组。

## 四、文件边界

- 路径固定为 `app/src/main/assets/web/help/md/updateLog.md`（注意无下划线），App 内帮助文档同步使用。
- `CHANGELOG.md` 是从 git 提交自动生成的清单，与本文档分工不同：前者机器生成、后者面向用户人工维护，两者并存不重复。
- 发布正文 = 本文档首个日期分组 + CI 自动生成的「PR / 贡献者」章节（`.github/scripts/release-notes.mjs`，规则见 `ci-cd.md`）；贡献者章节不要手写进本文档。
- 更新日志改动与对应功能改动同批提交，不留"事后补日志"的孤立提交，避免行为与日志脱节。
